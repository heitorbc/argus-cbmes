## Por que mudar

Após S2.10.9, a API ficou enxuta (Postgres-puro nos GETs, sem `syncIfStale`
fire-and-forget). Mas restavam 2 fontes de sync automático:

1. **`@Cron('0 0 0,6,12,18 * * *')`** — 4 ciclos/dia × 8 sources = 32 syncs
2. **`onModuleInit` → `syncAll('startup')`** — toda vez que o Render reinicia
   o app (sleep + wake é frequente no plano free), todas as 8 sources rodam
   em paralelo

Como o Tech Lead reportou ("alto tempo de apresentação dos dados na tela"),
o Render entrava em sync automático justamente quando o usuário acordava o
serviço — criando picos de latência e contenção no pool Postgres.

Decisão (2026-05-20): **sync 100% sob demanda**. Lag de dados aceitável
pois cada planilha tem regra de antecedência (Trocas 2 dias, Dispensas
alguns dias, QDI muda só quinta/sexta, ChOp <1 alteração/mês). MF CIODES
segue real-time (decisão D4 mantida do S2.10.9a).

## Achados

- **`@nestjs/schedule` era o único cron**: o `grep` confirmou que nenhum
  outro módulo usa `@Cron`/`@Interval`/`@Timeout`. Drop seguro.
- **`useQuery` reduz código em ~30%**: cada página migrada perdeu o bloco
  `useEffect` + `setLoading` + `setError`. Padrão consistente com S2.10.9c.
- **`viaturas.tsx` precisava de 2 fetches em paralelo**: agreguei num único
  `queryFn` retornando `{ enr, list }`. Simplifica invalidação.
