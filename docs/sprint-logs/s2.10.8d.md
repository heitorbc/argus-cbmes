# Sprint S2.10.8d — Militar consolidado em Postgres + 3 sources (Efetivo, QDI 1ª1º, QDI/DADOS)

**Data:** 2026-05-19
**Foco:** Fechar o roadmap S2.10.8 migrando o consolidado do `EfetivoService`
para Postgres com 3 sources independentes no SyncOrchestrator. Resolve o gap
descoberto em S2.10.7e (`prisma.militar` só era populado via auto-upsert de
Dispensas/Trocas).
**Tech Lead:** 2º SGT Heitor Barcellos Coelho

## Critérios de Pronto (DoD)

- [x] `MilitarConsolidatorService` novo — consolida 3 fontes + upserta em
      `prisma.militar` (inflight lock evita consolidação duplicada quando o
      `SyncOrchestrator.syncAll` roda em paralelo).
- [x] 3 ImportServices novos (`EfetivoImportService`, `QdiImportService`,
      `QdiDadosImportService`) implementando `SyncSource` — registrados no
      `SyncOrchestratorModule`.
- [x] `EfetivoService.list/getAll/findByNf` passam a ler de Postgres via
      `consolidateFromDbOrMemory()`. Fallback automático para consolidação em
      memória quando `prisma.militar` está vazio (cold boot antes do 1º sync).
- [x] Filtro `incluirEfetivoOrfao` aplicado em runtime usando a coluna
      `origensFonte` (NF cuja única origem é `EFETIVO` é filtrada quando
      `incluirEfetivoOrfao=false`).
- [x] `papelEspecial='Chefe de Operações'` persistido junto na consolidação
      (lógica do `EfetivoService.consolidate()` lines 221-248 migrada para o
      consolidator).
- [x] 7 testes novos do `MilitarConsolidatorService` cobrindo upsert,
      idempotência, inflight lock, falha de 1 source, ChOps habilitados, ChOps
      de outras Cias, e falha das 3 fontes.
- [x] Pipeline: typecheck + lint + format + test todos verdes
- [x] 671 testes totais (641 api + 30 web) passando

## Entregas

### Backend (apps/api)

**[apps/api/src/modules/efetivo/militar-consolidator.service.ts](apps/api/src/modules/efetivo/militar-consolidator.service.ts)**
(novo)

- `consolidateAndUpsert()`: lê caches dos 3 services
  (`EfetivoService.getRawEfetivoByNf`, `QdiService.getByNf`,
  `QdiDadosService.getByNf`), roda `mergeThreeSources()` com
  `incluirEfetivoOrfao=true`, enriquece com ChOps habilitados (ganho de
  `papelEspecial`), e faz upsert por NF em `prisma.militar`.
- **Inflight lock**: chamadas concorrentes compartilham a mesma Promise. Ao
  rodar `SyncOrchestrator.syncAll('cron')` os 3 ImportServices disparam em
  paralelo, mas só haverá 1 consolidação física; todos recebem o mesmo
  resultado (e cada um grava seu próprio SyncLog com counts compartilhados).
- **Não remove NFs ausentes**: militares que saíram da planilha continuam
  em Postgres para não quebrar FKs (Dispensa, Atestado, Ferias). Soft
  delete fica para sprint futura.
- **Try/catch por entry** (padrão S2.10.8b-fix): erro em 1 upsert vira
  inconsistência, não interrompe os demais.

## Achados

- **Counts compartilhados nos 3 SyncLogs por ciclo** é uma redundância
  intencional. Cada source loga "participei do ciclo X com counts (a,b,c)" —
  os 3 logs por ciclo cron mostram counts iguais pois é a mesma consolidação
  física graças ao inflight lock. Aceito como custo do design "3 sources
  independentes no menu" + "1 consolidação física".
- **`prisma.militar` armazena tudo (com órfãos)** e o filtro
  `incluirEfetivoOrfao` é runtime via `origensFonte`. Mantém compat com S6c/F1
  (NomeMatcher precisa de órfãos para resolver militares de escalas antigas).
- **NFs ausentes não são removidas** de `prisma.militar` para não quebrar FKs
  de Dispensa/Atestado/Ferias. Trade-off conhecido: militar que sai do efetivo
  pode aparecer "fantasmagoricamente" em queries. Soft delete fica para sprint
  futura quando houver volume real de saídas.
- **Tests existentes do EfetivoService precisaram de stub do Prisma**: o
  `count()` stub retorna 0 → todos os cenários originais (que validavam a
  consolidação em memória) seguem passando.
