## Por que mudar

### Item 1 — Escalas mensais sumindo

Tech Lead reportou: NF 3037509 deveria ver 29/05, 02/06, 06/06, 10/06 nos próximos 15 dias mas a /agenda devolvia 0 entries de Escala Mensal.

**Causa raiz:** [escalas.service.ts:280-329](apps/api/src/modules/escalas/escalas.service.ts) tinha filtro estrito:

```ts
if (c.militar.nf !== nf) continue;  // sempre passa (c.militar.nf=undefined)
```

O parser XLSX original ([escala-xlsx-parser.ts](apps/api/src/modules/escalas/escala-xlsx-parser.ts)) nunca preencheu `militarNf` no `ComposicaoEntry`. Em Postgres, `militarNf` é sempre `null`. Filtro estrito descartava silenciosamente TODAS as entries — desde S2.10.11a.

**Histórico:** PR #90 (S2.10.11d) tinha um fix completo + Mergulho/Salvamar + endpoint `/agenda/_trace`. Foi fechada sem merge na reversão S2.10.12 (modo WEB). Este PR reaplica APENAS a parte mínima (NomeMatcher fallback), sem reabrir as outras features.

### Item 2 — Filtros de tempo desalinhados

Botões 30/60/90d + checkbox "Incluir passado (30d)" não cobriam o caso de uso real: consulta retroativa por mês fechado, range arbitrário, e "próximos 15 dias" como default operacional.

## Decisões confirmadas (2026-05-28)

- **Fix backend**: NomeMatcher fallback em runtime (sem migration, sem re-import)
- **AgendaCard home**: mantém 30d hardcoded (resumo curto; controle fino só na /agenda full)

## Achados

- **NomeMatcher já cobre 4 níveis** (NF direto → posto+nome → nome só → tokens NFD) com flag de ambiguidade. Reuso direto sem precisar criar lógica nova.
- **`coletarEscalaEspecial` já fazia lookup lazy do efetivo** dentro de si. Agora recebe por parâmetro — 0 chamadas extras (apenas 1 total).
- **prisma-test-mock** precisava suportar `include.composicaoEntries` no `findMany` (era só `findUnique`).
- **`api.agendaRange` substitui `api.agendaProxima`** unificando todos os casos. Backend `/range` aceita até 90 dias — cobertura natural dos 4 modos.
