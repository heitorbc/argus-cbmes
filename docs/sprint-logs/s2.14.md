## Por que mudar

Hoje a sincronização da escala de ChOp é **global e em bloco**: o botão "🔄 Sincronizar" na página `/chefes-operacoes` re-importa todas as 12 abas mensais em paralelo. Problemas:

1. **Caro e arriscado**: re-baixa todos os meses mesmo que apenas 1 tenha sido editado; mais chance de falha parcial; `DELETE + INSERT` por mês pode rebuildar dados estáveis sem necessidade.
2. **Sem controle de "novo mês"**: para iniciar JUNHO/2026 (quando o sargenteante cria a aba na planilha), o Tech Lead precisava re-sincronizar tudo, sem feedback incremental.
3. **Mistura "carga inicial" com "atualização"**: o mesmo botão servia para popular DB vazio (correto) e para atualizar 1 mês (overkill).

A mudança torna o fluxo **mais granular e previsível**: cada ação corresponde a 1 intenção clara, o backend responde de forma discriminada (sucesso vs. aba indisponível), e a UI guia o usuário pelo estado correto.

## Achados

- **Sanity check em `syncMonth`**: detectei que sem ele, se a aba foi renomeada (ex.: planilha agora tem "MAIO 2027" no lugar de "MAIO 2026"), o parser extrairia `(2027, 5)` mas o caller esperava `(2026, 5)` — o DB acabaria com dado errado escrito sob a chave certa. Adicionada rejeição explícita: aba devolve ano/mes diferente → ServiceUnavailableException descritiva.
- **Erro classificável por regex**: o parser lança `"Cabeçalho \"NOME DE GUERRA\" não encontrado no CSV de ChOp."` ou `"Não foi possível determinar ano/mes da planilha ChOp."` quando a aba não existe (gviz retorna HTML em vez de CSV). HTTP 404 também acontece. Os 3 padrões cobrem o caso "aba ausente". Mais robusto que tentar parsear o erro pelo type.
- **Frontend auto-navega após "Buscar próximo"**: `setAno/setMes` move o dropdown para o mês recém-importado. Sem isso o usuário teria que clicar para selecionar manualmente. Detalhe pequeno mas reduz fricção significativamente.
- **`CHOP_SHEET_NAMES` override preservado**: helper `monthSheetName` faz match reverso via `parseAnoMesFromSheetName` para que ambientes com naming custom (ex.: "ChOp-Maio-2026") continuem funcionando. Se o override não cobre (ano, mes), cai no default + warn log.
- **Endpoint bulk `POST /integracoes/chefes-operacoes/sync` preservado**: usado pela carga inicial via UI, e continua disponível em `/configuracoes/integracoes` como fallback admin emergencial. Não removi para evitar quebrar fluxos administrativos não-documentados.
- **`syncMonth` não usa `inflight` lock**: o lock atual do `syncToDatabase` (bulk) cobre apenas concorrência da operação grande. Operações single-month são rápidas (~2-3s) e re-entrant safe pela transaction. Locking fica para sprint futura se concorrência virar problema.
