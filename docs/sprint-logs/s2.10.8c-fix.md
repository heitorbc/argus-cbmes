# Hotfix S2.10.8c-fix — `/configuracoes/integracoes` retorna 500 em cold boot

**Data:** 2026-05-19
**Foco:** Após reinício da API (Render/Supabase cold boot), o GET
`/integracoes` retornava **Internal Server Error** na 1ª chamada. Segundos
depois, a 2ª request carregava normalmente.
**Tech Lead:** 2º SGT Heitor Barcellos Coelho

## Sintoma reportado

> "ao tentar acessar o modulo de integrações está sendo apresentado o
> seguinte erro: Internal server error. e após algum tempo foi realizdo o
> carregamento normal da planilha."

## Raiz da causa

Duas fragilidades acumuladas desde o S2.10.8c que se manifestam em cold boot
do Supabase:

1. **`IntegracoesService.buildStatus()` não tem try/catch.**
   ([apps/api/src/modules/integracoes/integracoes.service.ts:262-285](apps/api/src/modules/integracoes/integracoes.service.ts#L262-L285))
   `list()` é `Promise.all(sources.map(buildStatus))`. Se **qualquer** source
   lança em `getStatus()`, o `Promise.all` rejeita e a exceção sobe sem
   handler → HTTP 500 no menu inteiro.

2. **`IseoHospitaisService.getSyncStatusAgregado()` chama
   `prisma.iseoHospitalEntry.count()` sem try/catch.**
   ([apps/api/src/modules/iseo-hospitais/iseo-hospitais.service.ts:96-104](apps/api/src/modules/iseo-hospitais/iseo-hospitais.service.ts#L96-L104))
   Em cold boot do Supabase, a primeira query Prisma pode falhar (pool
   exausto, connection terminated, timeout). Combinada com (1), derruba a
   lista inteira.

A 2ª request funciona porque o Supabase já conectou e o `count()` retorna 0
normalmente.

## Correção

### Fix 1 — `buildStatus()` graceful

[apps/api/src/modules/integracoes/integracoes.service.ts](apps/api/src/modules/integracoes/integracoes.service.ts)

Try/catch em torno de `await s.getStatus()`. Se lança:

- `this.logger.warn('getStatus de {id} falhou (...). Exibindo como "nunca".')`
- Retorna `status = { syncedAt: null, count: 0, stale: false }` (vira label
  `'nunca'` na UI, igual a uma source nunca sincronizada).

Garante que 1 source quebrada **não derruba** o menu inteiro.

### Fix 2 — `getSyncStatusAgregado()` defensive

[apps/api/src/modules/iseo-hospitais/iseo-hospitais.service.ts](apps/api/src/modules/iseo-hospitais/iseo-hospitais.service.ts)

Try/catch em torno do `prisma.iseoHospitalEntry.count()`. Se lança, fallback
`count = 0` + log warning. Mesmo padrão usado em
[efetivo.service.ts:138-145](apps/api/src/modules/efetivo/efetivo.service.ts#L138-L145).

## Verificação end-to-end

```bash
pnpm typecheck && pnpm lint && pnpm format:check && pnpm test
```

Pós-deploy (Render):

1. **Restart API** → 1ª request `GET /integracoes` retorna 200 com a lista
   completa (sources cujo `getStatus()` falhar aparecem como `status='nunca'`
   ao invés de derrubar tudo)
2. **Log esperado quando Supabase está frio**:
   ```
   [IseoHospitaisService] prisma.iseoHospitalEntry.count() falhou: Connection terminated. Retornando count=0.
   [IntegracoesService] getStatus de 'iseo-hospitais' falhou (...). Exibindo como 'nunca'.
   ```
   (Apenas se ambos os fixes forem necessários simultaneamente — o Fix 2
   normalmente cobre o caso antes do Fix 1.)
3. **Smoke**: `curl http://api/integracoes -b /tmp/c.txt | jq 'length'` retorna 13

## Achados

- **Try/catch defensivo em prisma.count()** deveria ser o padrão para queries
  que servem o menu de integrações: o menu não pode depender de cold-boot
  Supabase pra abrir.
- **`Promise.all` sem isolamento** é o anti-pattern central. O Fix 1 isola
  caso a caso, sem mudar a semântica geral (paralelismo continua).
- **Cold boot Supabase**: pool de conexão se estabiliza em ~5-10s. Render
  reinicia o app a cada deploy; este hotfix garante que o menu de integrações
  não falha durante esses primeiros segundos.
