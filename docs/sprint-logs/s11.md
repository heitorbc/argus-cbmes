## Estratégia "builder puro + StreamableFile"

O builder é uma função pura `ParteDiaria → Buffer`. Não toca
filesystem, não chama service. Vantagens:

1. **Testável sem mock pesado** — tests passam um shape literal,
   inspecionam o resultado via JSZip.
2. **Service-agnostic** — pode ser reutilizado se um dia exportar PD
   via cron job, e-mail anexado, etc.
3. **Cache-friendly** — o controller cuida só de `get(data)` + chamada
   ao builder. Se um dia formos cachear, basta cache no service.

O controller usa `StreamableFile` (NestJS) em vez de `res.send(buffer)`
direto para preservar interceptors e middleware (logging,
compression).

## Por que sem PDF server-side?

- **Puppeteer** (Chromium) adiciona ~200MB ao build. Vercel functions
  têm limites de bundle.
- **Backend hosting indefinido** (Vercel x Render x Railway — ver
  CLAUDE.md). Adotar Puppeteer agora amarra para Render/Railway.
- **`window.print()` cobre o caso de uso** no curto prazo. O Fiscal
  imprime ou salva como PDF pelo diálogo nativo do navegador.
- **DOCX é o formato institucionalmente mais útil** — entra direto no
  e-Docs como anexo editável, sem precisar de OCR ou conversão.

PDF server-side fica para sprint dedicada após a decisão de hosting.

## Achados durante a implementação

- **`Buffer.kmInicial != null` reprovado pelo ESLint** (`eqeqeq` rule).
  Trocado para `!== null` — comportamento idêntico, lint passa.
- **`Header` decorator** sozinho cobre `Content-Type`. `@Res({
passthrough: true })` permite setar `Content-Disposition` dinâmico
  (filename muda por data) sem desativar o `StreamableFile`.
- **`jszip` como devDep:** lib `docx` não expõe API para inspecionar o
  XML gerado. JSZip abre o pacote `.docx` (que é um zip) e dá acesso a
  `word/document.xml`. Mais robusto do que mockar o gerador.
