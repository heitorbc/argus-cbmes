## Por que mudar

Conforme entrevista 2026-05-28 com o Tech Lead: o **Mapa Força CIODES** é uma planilha estática que dita os recursos disponíveis da unidade. Para abrir o sistema a outras unidades (3ª CIA IND COLATINA, PAB Baixo Guandu) sem precisar reescrever a planilha CIODES toda vez que houver mudança institucional, é necessário **inverter** a integração:

- **Hoje (antes desta sprint):** CIODES é fonte; Argus consome.
- **Após S2.13e:** Argus é fonte; CIODES não é mais consultado em runtime. Em sprint futura S2.14, Argus passa a publicar atualizações no CIODES via Puppeteer (write-only).

Esta sprint NÃO remove o `MapaForcaCiodesService` — ele segue no módulo e no `/health/status` — apenas não é mais chamado por `MapaForcaService`. Isso permite reaproveitar a autenticação/parsing quando S2.14 implementar a publicação.

## Achados

- **`composicaoAtualMf` perde dados**: a CIODES preenchia chefe/motorista/operadores via real-time. Com Argus como fonte, esses campos ficam `undefined`/`[]` no payload. O frontend já lida graciosamente (Map vazio = sem composição). Aceito como tradeoff do desacoplamento; recuperação dessa "composição real-time" ficaria em S2.14 quando Argus virar fonte completa.
- **`vtrStatus` derivado de QDV**: ARGUS já tem o status real das viaturas pelo QDV (DISPONIVEL/BAIXADA/EMPRESTADA), não precisa do CIODES. Helper detecta a viatura associada via `viaturaPrefixoFixo` (S2.13b) ou via `funcaoOperacional`. Para recursos sem viatura associada (ex.: GUARDA, DRO/TELEFONISTA), `vtrStatus` fica null — comportamento idêntico ao CIODES legacy.
- **`composicaoMf` continua funcionando**: o builder `buildComposicaoMf` recebe o mesmo formato `{ recurso, vtrPrefixo, vtrStatus }` que esperava; tripulação vem da escala (XLSX) e a estrutura final é a mesma.
- **CIODES injetado mas inutilizado**: optei por manter `mapaForcaCiodes: MapaForcaCiodesService` no constructor (com comentário explicativo) em vez de remover. Isso preserva o módulo para S2.14 (write para CIODES) sem novo refactor.
- **Default `UNIDADE_1CIA_1BBM_ID`**: garante back-compat. Para usuários da 3ª CIA acessarem seu MF, frontend precisa enviar `?unidade=` (S2.13f vai integrar no UI). Não-admin ficará amarrado a `user.unidadeId` (S2.14 com filtro fino).
- **Tests `FakeRecursosService`**: faço-o como classe simples retornando o mesmo array de 3 recursos hardcoded para preservar contratos dos 34 testes. Refactor maior (cada teste declarando seus recursos via fixture) fica como débito documentado.
