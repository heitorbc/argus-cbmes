## Motivação

S2.10.1 entregou o schema Prisma + migration `init` aplicada no Supabase. Este sub-sprint efetiva o primeiro service usando Prisma como source-of-truth, deixando o Map em-RAM pra trás.

AuthService foi escolhido como primeiro porque:

1. **Toca rota crítica** (login/logout/changePassword) — se quebrar, pega fácil em smoke test
2. **Modelo simples** (1 tabela `users`) — menor risco arquitetural pra estabelecer o padrão
3. **Já tinha CRUD admin** (S2.7) — exercita todos os 4 verbos Prisma de uma vez
4. **Sem dependência de outras tabelas** — pode rodar isolado do resto da migração

## Mudanças

### `PrismaService` (novo)

`apps/api/src/common/prisma/prisma.service.ts` + `prisma.module.ts`. Singleton injetável, `OnModuleInit` faz `$connect`, `OnModuleDestroy` faz `$disconnect`. Decorado com `@Global()` para não precisar reimportar em cada feature module.

### Refactor AuthService

| Método           | Antes                              | Depois                                                                                                   |
| ---------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `login`          | `users.get(nf)` + `bcrypt.compare` | `prisma.user.findFirst({where: {nf, deletedAt:null}})` + bcrypt + fire-and-forget `update ultimoLoginEm` |
| `changePassword` | `users.set(...)`                   | `prisma.user.update({where, data})`                                                                      |
| `loginAsPersona` | `users.get(nf)`                    | mesmo findFirst                                                                                          |
| `listPersonas`   | `Array.from(users.values())`       | `findMany({select})` — agora **async**                                                                   |
| `getCurrentUser` | sync `users.get`                   | **async** findFirst                                                                                      |
| `listUsuarios`   | sync map                           | **async** `findMany({orderBy:{nome:'asc'}})`                                                             |
| `createUsuario`  | `users.set` + senha hash           | `create` (com lógica de ressuscitar soft-deleted)                                                        |
| `updateUsuario`  | mutação direta no objeto           | `update({where, data})`                                                                                  |
| `removeUsuario`  | `users.delete` (hard)              | **soft delete** `update({where, data:{deletedAt: new Date()}})`                                          |

### Soft delete em users

Implementação concreta do ADR-014 D4: `removeUsuario` agora marca `deletedAt` em vez de DELETE. `findFirst` filtra por `deletedAt: null` em todos os caminhos de leitura. Permite auditoria histórica (quem foi removido, quando) e ressuscitar via re-create (mesmo NF).

### Seed

`apps/api/prisma/seed.ts`:

- Lê `MOCK_USERS` (11 entradas)
- Re-hasheia a senha default (`batalhao01`) com `BCRYPT_COST` do ambiente
- `upsert` por NF — `create` se novo, `update` mantém nome/posto/ant/papeis e **NÃO sobrescreve senhaHash** (preserva senhas já trocadas pelos usuários reais)
- Roda via `pnpm --filter api prisma:seed` (usa `.env.local` da raiz via dotenv-cli)

Executado contra Supabase real: ✅ **11 usuários criados** em `public.users`.

### Tests

Mantida a estratégia de testes simples (sem `Test.createTestingModule`). Adicionado helper `makePrismaMock(seed)` que implementa um `Map<nf, User>` cumprindo o subset do Prisma API que o AuthService usa (`findFirst`, `findUnique`, `findMany`, `update`, `create`).

Tradeoffs:

- ✅ Sem dependência de Postgres no test runner — CI roda sem Supabase
- ✅ Tests rápidos (24 em 211ms vs ~10s antes)
- ⚠️ Não detecta erro de query Prisma (ex.: campo inexistente) — Typecheck cobre isso
- ⚠️ Não testa cascade/transação real — fica pra integration tests futuros (não escopo S2.10)

## Riscos identificados

| Risco                                                | Mitigação                                                                                                |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `mock-users.ts` em produção após seed = confusão     | Sprint log marca claramente que o arquivo é **só source do seed** agora; deletar em S2.10.5              |
| Re-rodar seed sobrescreve dados editados em produção | `upsert.update` foi cuidadosamente escrito pra preservar `senhaHash` — só atualiza nome/posto/ant/papeis |
| Falha de pool em Vercel serverless                   | `DATABASE_URL` está com pooler 6543 + `connection_limit=1` (config do runbook)                           |
| Migration adicional em S2.10.3+ falha em produção    | Vercel build vai falhar se `migrate deploy` falhar — bloqueia merge automático                           |
