## Por que mudar

O Tech Lead descreveu na entrevista que o Oficial de Operações da unidade precisa de uma tela onde possa cadastrar quais recursos a unidade possui ativos, definir se cada um conta com viatura, equipe ou ambos, e qual a equipe mínima. Hoje:

- A página `/cadastros/recursos` existe (admin-only) mas é orientada à configuração técnica do MF, não ao caso de uso operacional
- Não havia UI para `tipoComposicao` (introduzido em S2.13b)
- Não havia editor de `equipeMinima` (introduzido em S2.13b)
- A nova role `oficial_operacoes` (criada em S2.13c) precisava de um destino real

S2.13d entrega a tela que destrava o Oficial de Operações a configurar recursos sem depender do admin.

### Frontend

**[apps/web/src/pages/operacoes/recursos.tsx](../../apps/web/src/pages/operacoes/recursos.tsx)** (REWRITTEN)

Substitui o placeholder de S2.13c por uma página completa. Estrutura:

1. **Header** — Título + botão "Voltar" ao home
2. **Seletor de unidade** — `<select>` com unidades visíveis (admin: todas; demais: apenas a própria). Mostra `nome (codigo) · tipo` em cada opção.
3. **Lista de recursos** — master-detail, ordenados por `ordem`. Cada item exibe:
   - `#ordem · nome` (linha 1)
   - `categoria · tipo de composição [· viatura fixa] [· N funções na equipe mínima]` (linha 2)
   - Botões "Desativar"/"Ativar" (amber/emerald) + "Editar"
   - Inativos ficam com `opacity-60`
4. **Botão "+ Novo recurso"** abre form vazio com `ordem = N+1`
5. **Formulário** (cria ou edita):
   - **Nome** (text, obrigatório)
   - **Categoria** (dropdown 4 opções: OPERACIONAL, STAFF, AQUATICA, GUARDA)
   - **Ordem** (number)
   - **Tipo de composição** (radio com 3 opções rotuladas)
   - **Equipe mínima** (textarea JSON, visível apenas se tipo ≠ viatura_only). Placeholder mostra exemplo válido + descrição do shape `{ funcao, obrigatorio, podeAcumularCom? }`. Parse + erro inline em caso de JSON inválido.
   - **Viatura fixa** (text opcional). Vazio = qualquer viatura do tipo
   - **Ativo** (checkbox)
   - Botões "Salvar" / "Cancelar"
6. **Derivação automática**: ao criar, `comportaViatura`/`comportaEfetivo` derivam de `tipoComposicao` para back-compat com schema existente

**Tratamento de erros:**

- Erro do backend (ApiError) → mensagem na inline em vermelho
- JSON inválido em equipeMinima → erro inline (sem submit)
- Erro de listagem (ApiError) → banner vermelho no topo

## Achados

- **Editor de equipeMinima via JSON textarea**: decisão deliberada para MVP. Um editor visual ("adicionar função" → linha por linha com checkbox obrigatório + chips de acumulação) é muito superior em UX mas dobraria o esforço da sprint. JSON funciona para Tech Lead admin testando + permite copy/paste entre recursos. Iteração visual fica para S2.14.
- **Filtro de unidades**: hoje o frontend usa `user.unidadeId` direto (sem chamar API de descendentes). Funciona para sargenteante de companhia ver só a companhia. Para "ver companhia + postos avançados ligados a ela" precisaria expor o helper `visiveisParaUsuario` do backend via novo endpoint — fica S2.14.
- **Derivação `comportaViatura`/`comportaEfetivo`**: optei por derivar automaticamente em vez de adicionar inputs duplicados. Isso simplifica a UX (oficial não precisa saber das flags antigas) e mantém o schema válido.
- **Sem novos testes web**: a página é UI integrada complexa; testes unitários teriam baixa cobertura útil sem integração com MSW (mock service worker). Smoke pós-deploy é a validação primária. Vitest + RTL para essa página é débito conhecido (S2.14).
- **Backend ainda não filtra por unidade visível**: confiar no frontend é OK para MVP onde admin/oficial_operacoes são papéis confiáveis. Backend gate fino (oficial da 3ª CIA não pode editar recurso da 1ª Cia) precisa do middleware compartilhado de `unidadesVisiveisParaUsuario` — S2.14.
