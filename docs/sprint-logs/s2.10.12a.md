## Por que mudar

ARGUS é **mobile-first absoluto** desde S0 — toda página estritamente
`max-w-md` sem nenhum breakpoint Tailwind. Isso serve para o Fiscal de
plantão e o operacional em campo, mas **não serve para o público que passa
o dia em desktop dual-screen**: sargenteante (escalas, dispensas,
atestados, trocas, NS), oficial de operações, comandante, logística.

Em desktop a UI atual aproveita ~25% do viewport, lista vertical apertada,
formulários em modais empilhados, sem master-detail, sem atalhos de
teclado. Refazer em responsive puro não escala: a UX precisa ser
**arquiteturalmente diferente** (split-view, tabelas largas, sidebars
fixas, edição inline), não só layout maior.

**Solução**: dois modos coexistentes selecionáveis pós-login. Mobile
permanece intacto; WEB é uma camada paralela com seu próprio shell e
páginas dedicadas (a serem criadas em sub-sprints S2.10.12b–e),
compartilhando hooks de dados (`useQuery`) com a versão mobile.

Esta sub-sprint **S2.10.12a entrega a fundação**: tudo que é preciso
para a escolha funcionar end-to-end (picker → shell adequado → toggle
para trocar). As páginas WEB específicas ficam para as próximas sub-sprints.

## Achados

- **`window.location.reload()` é o caminho mais simples** após trocar
  modo. Tentamos transição parcial mas o re-mount do router via
  `setMode + navigate` causa flash de UI mista. Reload é instantâneo
  graças ao localStorage cache do React Query (S2.10.9c).
- **Sidebar auto-collapse em <1280px** vs viewport hint em 1024 — gap
  intencional: usuário em monitor 1280 ainda escolhe WEB, mas a sidebar
  inicia recolhida para preservar área útil.
- **Framer Motion não é carregado em mobile**: o `MobileShell` não
  importa; só `WebShell` e `mode-picker`. Tree-shaking do Vite preserva.
- **RBAC dentro do WebShell**: cada item do nav passa por `canAccessRoute`;
  grupo inteiro sumindo se nenhum item visível. Garante consistência
  visual com home mobile.
